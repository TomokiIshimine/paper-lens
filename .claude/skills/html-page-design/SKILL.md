# html-page-design — リッチ HTML 記事ページデザインと GitHub Pages 公開の単一真実源

確定済み Markdown 記事（`output/<記事>.md`）とカバー画像（`cover.png`）から、量産しても統一感の崩れない「リッチでデザインされた HTML 記事ページ」を執筆し、GitHub Pages（公開元 = `main` ブランチ `docs/` 配下）へ公開するための、デザイン規約・共有外部 CSS の実体・公開手順・観点別の合否判定基準を定める How スキル。

生成側（`article-html-author`）とレビュー側（`html-reviewer`）が同じ基準を参照することで、生成⇄レビューの判定ズレを構造的に防ぐ（DRY）。これは `infographic-design` と同型のパターンである（生成側とレビュー側が単一真実源を共有する）。

## 適用場面

`write-article` ワークフローの HTML 工程（`output/<記事>.md` 確定後の後段ステップ）が参照する。本工程は HTML 整形・デザイン適用に限る（後述「本文ファクト不点検の原則」に従う）。

- **生成側** — `article-html-author` が記事 HTML（`docs/articles/<記事スラッグ>.html`）と記事一覧トップ（`docs/index.html`）を初回執筆・再生成する際、本スキルの「デザイン観点・品質基準」「共有外部 CSS」「ページ骨格とレイアウト規約」「記事一覧トップページ index.html の規約」に従って構造・コンポーネントを設計し、本スキルの「公開元ディレクトリ規約」「公開手順」に従って配備・公開する。
- **レビュー側** — `html-reviewer` が担当 1 観点を点検する際、本スキルの「観点別判定基準」から該当観点の合否基準を引いて判定する。

本スキルは「良いリッチ HTML 記事ページの基準」と「公開規約」の単一真実源であり、生成側・レビュー側のいずれもこれらの基準を自プロンプトへハードコードせず本スキルを参照する。観点識別子（`design-consistency` / `readability` / `infographic-richness` の 3 観点）・宣言順（`design-consistency` → `readability` → `infographic-richness`）・反復制御（反復上限 2 周）は `write-article` SKILL.md の `<html-review-aspects>` が保持し、本スキルは各観点の判定基準（チェック項目・合否閾値）を提供する（`/multi-aspect-review` の役割分担を踏襲）。

### 本文ファクト不点検の原則

本工程では本文の事実・主張は確定済み（`output/<記事>.md`）であり、HTML 整形・デザイン適用に限る。以下を本スキル全体の前提とし、生成側・レビュー側・各観点節はこの原則に従う（各所で全文を再掲せず本節を参照する）。

- **本文ファクトは再点検しない** — 本文の事実・主張・数値の正否は HTML 工程の対象外。視覚化候補（数値・対比・手順・フロー）の抽出は確定 Markdown 本文を根拠とする。
- **視覚化で本文の意味を歪めない** — 視覚化は本文の意味を保つ整形であり、本文にない主張・数値・因果を視覚要素として足さない。本文と矛盾するハイライト等の意味改変はしない。

## デザイン観点・品質基準

「良いリッチ HTML 記事ページ」が満たすべき要件。

- **量産しても統一感が崩れない** — 配色・タイポグラフィ・レイアウト・コンポーネントは共有外部 CSS（後述）に集約され、記事ごとに見た目がブレない。記事 HTML 側にデザインを `<style>` で直書きしない。
- **日本語長文の可読性が高い** — 読みやすい本文幅（1 行の文字数が多すぎない）、ゆったりした行間、見出しと本文の十分な余白、本文と背景の高いコントラストを満たす。
- **構造が意味的に正しい** — 見出し階層（`h1` → `h2` → `h3`）が論理順序で入れ子になり飛び級しない。本文・図表・引用・用語集・原論文リンクが適切な HTML 要素（`<figure>`/`<blockquote>`/`<dl>` 等）と所定のクラスでマークアップされる。
- **リッチだが崩れない** — カバー画像・図表・コードブロック・数式・テーブル、および後述「ビジュアルコンポーネント規約」の各コンポーネントが、狭い画面でもはみ出し・重なり・見切れを起こさない（レスポンシブ）。
- **インフォグラフィック性（視覚的理解支援）が高い** — 本文の主要素（課題・手法・主要結果数値・比較・時系列・処理フロー）が、プレーンな見出し＋段落＋箇条書きだけでなく、意味に応じたビジュアルコンポーネント（後述「ビジュアルコンポーネント規約」）で視覚化され、読み手の本文理解を助ける。装飾目的だけの図は置かない。`infographic-design` の設計思想（数値・図が主張を支える／視線誘導が成立する／情報ブロックは欲張らない＝1 画面・1 セクションあたり 3〜5 個目安）を HTML 向けに反映する（視覚化は前述「本文ファクト不点検の原則」に従う）。
- **エントリ動線が成立している** — 記事一覧トップ（`index.html`）から各記事へ、各記事から一覧へ、迷わず辿れる。

## 共有外部 CSS

全記事 HTML のデザインは、**1 枚の共有外部 CSS に集約する**。これにより量産時のデザイン統一が保たれ、1 箇所の変更で過去記事を含む全 HTML へ波及する。

- **単一真実源の所在** — 共有 CSS の実体は本スキル配下 `assets/style.css`（`.claude/skills/html-page-design/assets/style.css`）に同梱されている。これが全記事共有 CSS の**単一真実源**である。
- **真実源と配備物の関係** — 公開時、`article-html-author` は本スキルの `assets/style.css` を公開元 `docs/assets/style.css` へ**配備（コピー）**する。`docs/assets/style.css` は配備物であり、真実源ではない。
- **記事 HTML からの参照** — すべての記事 HTML および `index.html` は、この共有 CSS を `<link rel="stylesheet" href="...style.css">` で参照する（記事 HTML は `docs/articles/`、CSS は `docs/assets/` にあるため、記事ページからの相対参照は `../assets/style.css`、`index.html` からは `assets/style.css`）。デザインを記事 HTML 側に `<style>` でインライン定義しない。
- **CSS の更新手順** — デザインを変更したいときは本スキル内 `assets/style.css` のみを編集する。次回公開時の配備によって全記事へ波及する。`docs/assets/style.css` を直接編集しない（次回配備で上書きされ、真実源と乖離するため）。
- **CSS が保持するもの** — 配色（カラートークン）・タイポグラフィ（日本語可読フォントスタック・本文サイズ・行間）・レイアウト（本文幅・余白スケール）・コンポーネント（見出し階層・本文ブロック・図表/テーブル・引用・コード・数式コンテナ・用語集・カバー画像・原論文リンク・記事一覧カード・ヘッダ/フッタ）・レスポンシブ規則。これらの値は CSS が保持源であり、記事 HTML・各サブエージェントプロンプトに重複定義しない。

記事 HTML 側はこの共有 CSS が定めるクラス名（`.article`、`.article__cover`、`.article__title`、`.article__body`、`.glossary`、`.paper-link`、`.article-list`、`.article-card` 等）に沿って構造をマークアップする。クラス契約に従えば、デザインは CSS 側で一貫して適用される。

## ページ骨格とレイアウト規約

記事 HTML（`docs/articles/<記事スラッグ>.html`）の骨格。

- **文書ヘッダ** — `<!DOCTYPE html>`、`<html lang="ja">`、`<meta charset="utf-8">`、`<meta name="viewport" content="width=device-width, initial-scale=1">`、`<title>`（記事タイトル）、共有 CSS への `<link>`。
- **サイトヘッダ（`.site-header`）** — サイト名（一覧トップへのリンク）を置く。全記事共通。
- **記事本体（`.article`）** — 以下の順で構成する。
  1. **カバー画像（`.article__cover`）** — `cover.png` を `<img>` で 16:9 表示。詳細は下記「カバー画像の埋め込み方」。
  2. **記事タイトル（`.article__title`）** と **メタ情報（`.article__meta`）** — タイトルは `h1` 相当。メタには公開日等を置く。ここでの「公開日」は**論文（arXiv プレプリント）の公開日**を指し、記事執筆日・サイト掲載日ではない。値は確定情報（`output/<記事>.md` の frontmatter／本文）の論文公開日を根拠とし、本スキルで値を捏造しない。文言・命名・表記は `japanese-tech-writing` に従う（本スキルでは再定義しない）。
  3. **本文（`.article__body`）** — H2 見出しで章立てし、段落・リスト・図表・引用・コード・数式を所定のクラス/要素でマークアップする。見出し階層は飛び級しない。
  4. **用語集（`.glossary`）** — 用語の定義リスト。`<dl>/<dt>/<dd>` でマークアップ。用語集の内容・対象用語の選定は `japanese-tech-writing` に従う。
  5. **原論文リンク（`.paper-link`）** — 下記「原論文リンク」。
  6. **記事ナビ（`.article__nav`）** — 一覧トップへ戻る導線。
- **サイトフッタ（`.site-footer`）** — 全記事共通。

### カバー画像の埋め込み方

- 公開元での画像配置パスと記事 HTML からの `<img>` 参照を一貫させる。カバー画像は公開物として公開元（`docs/` 配下）に配置し、記事 HTML から相対パスで参照する。
- `<img>` には記事内容に即した `alt` を付す（可読性・アクセシビリティ要件）。画像本体は共有 CSS の `.article__cover img`（`aspect-ratio:16/9; object-fit:cover`）で表示が統一される。

### 原論文リンク

- `.paper-link` 領域に、原論文タイトルと arXiv（または DOI）への外部リンクを置く。リンクは `<a>` で URL を明示し、新規タブ運用とする場合も含めクリックで原論文へ到達できること。
- リンク先 URL・論文タイトルは記事の確定情報（`output/<記事>.md` の frontmatter／本文）を根拠とし、本スキルで値を捏造しない。

## ビジュアルコンポーネント規約

確定済み Markdown 本文を「インフォグラフィック風リッチ HTML」へ視覚化するためのコンポーネント群。本文のどの構造（数値・対比・手順・因果）を視覚化するためのものかという**用途**と対応付けて使う。各コンポーネントの配色・余白・タイポ・レスポンシブ規則の実体は共有外部 CSS（`assets/style.css`）が保持源であり、記事 HTML 側に `<style>` で直書きしない（クラス契約に沿ってマークアップすれば CSS 側で一貫適用される）。

- **要点カード（`.card` / `.card-grid`）** — 複数の要点・特徴を並列に提示する。`.card-grid` をラッパに、各要点を `.card` として並べる。本文中の並列な特徴・利点・構成要素の列挙を視覚化する用途。
- **数値ハイライト（`.stat` / `.stat__value` / `.stat__label`）** — 主要結果数値・指標を強調する。`.stat__value` に数値、`.stat__label` に指標名・単位・補足を置く。本文中の主要結果数値・性能指標を視覚化する用途。
- **比較表（`.compare-table`）** — 手法間・条件間の対比を表で示す。本文中の手法比較・ベースラインとの対比・条件別の差異を視覚化する用途。
- **タイムライン／ステップ（`.timeline` / `.timeline__step`）** — 手順・時系列・処理の段階を示す。`.timeline` をラッパに、各段階を `.timeline__step` として並べる。本文中の手順・時系列・処理パイプラインの段階を視覚化する用途。
- **処理フロー・ダイアグラム（`.diagram` ラッパ ＋ インライン SVG）** — 処理・関係・因果を図示する。`.diagram` 内にインライン SVG で図を描く。本文中の処理の流れ・コンポーネント間の関係・因果構造を視覚化する用途。
- **アイコン的強調・補足（`.callout` / `.badge`）** — 注意・ポイント・ラベルを強調する。`.callout` は補足ブロック、`.badge` はインラインのラベル。本文中の注意点・キーポイント・カテゴリラベルを強調する用途。

### 決定論的生成の制約

- ビジュアルは **HTML/CSS と インライン SVG／CSS 図形**で決定論的に描く。画像生成 AI・外部画像アセットに依存しない（カバー画像 `cover.png` を除く本文中ビジュアルは生成画像に頼らない）。
- 視覚化候補（数値・対比・手順・フロー）の抽出・視覚化は前述「本文ファクト不点検の原則」に従う（本文の意味を保つ整形に限り、本文ファクトの再点検・改変をしない）。

### リッチだが崩れない（新コンポーネントへの適用）

「デザイン観点・品質基準」の「リッチだが崩れない」要件（レスポンシブ・はみ出し防止）を上記の各ビジュアルコンポーネントにも適用する。狭幅でカードグリッドが段組み解除される、比較表が横スクロール可能になる、タイムライン・ダイアグラムが画面外へはみ出さない、といった崩れ防止を満たす（実体は共有外部 CSS のレスポンシブ規則が保持する）。

## 記事一覧トップページ index.html の規約

`docs/index.html` は GitHub Pages のエントリポイント（記事一覧トップ）である。

- **役割** — 公開済み全記事への入口。公開時、`article-html-author` が当該記事のエントリを追加・更新する（既存エントリは保持し、重複追加しない）。
- **骨格** — 記事ページと同じサイトヘッダ／フッタ・共有 CSS を用いる。本体は `.index` ラッパ内に、リード文（`.index__lead`）と記事カードのリスト（`.article-list` > `.article-card`）を置く。
- **記事カード（`.article-card`）** — 各記事につき 1 枚。サムネイル（カバー画像、`.article-card__thumb`）・公開日（`.article-card__date`）・タイトル（`.article-card__title`、記事 HTML への内部リンク）・要約（`.article-card__summary`）を含める。`.article-card__date` の「公開日」は**論文（arXiv プレプリント）の公開日**を指し、記事執筆日・サイト掲載日ではない。値は記事 HTML 側のメタ情報（`.article__meta`）と一致させる。要約・タイトル文言は `japanese-tech-writing` に従う。
- **並び順規約** — 新しい記事を上（先頭）に置く降順（論文公開日の新しい順）。新規エントリは先頭に挿入する。
- **エントリの一意性** — 記事スラッグをキーに、同一記事の重複エントリを作らない。再公開・再生成時は既存エントリを更新する。

## 公開元ディレクトリ規約

公開元 = `main` ブランチの `docs/` 配下（GitHub Pages の公開元設定に一致）。同一 `docs/` 内で設計ドキュメントと公開物を役割分離する。

- `docs/articles/<記事スラッグ>.html` — 記事 HTML（恒久公開物）。
- `docs/index.html` — 記事一覧トップ（Pages エントリポイント）。
- `docs/assets/style.css` — 全記事共有 CSS（本スキル `assets/style.css` の配備物）。
- `docs/assets/` 配下 — 共有 CSS・公開物カバー画像など公開アセット。
- `docs/architecture.md` — ワークフロー設計ドキュメント（公開物ではなく設計の地図）。公開物と同居するが役割が異なるため、公開物の生成・配備で `architecture.md` を改変しない。

記事スラッグの命名・記事ファイル名の規約は `japanese-tech-writing` の命名規約に従う（本スキルで再定義しない）。

## 公開手順

全工程（本文レビュー・画像レビュー・HTML レビュー）合格時のみ、`article-html-author` が GitHub Pages へ公開する。

- **add 対象** — 記事 HTML（`docs/articles/<記事スラッグ>.html`）、更新済み `docs/index.html`、共有 CSS の配備物（`docs/assets/style.css`、未配備または差分時）、公開物カバー画像。`docs/` 配下の公開物に限定し、`work/` などの中間生成物を add しない。
- **commit** — コミットメッセージは記事の公開が判別できる規約とする（例: 記事タイトルまたはスラッグを含める）。1 記事の公開を 1 コミットにまとめる。
- **push** — `origin main` 固定。**force push は禁止**。リモートの公開元設定に一致するブランチ（`main`）へ push する。
- **公開タイミング** — push は全検証ループ（本文・画像・HTML）合格時のみ。レビュー反復上限到達で打ち切られた場合・検証未完了の場合は push しない。再生成モード（HTML レビュー FAIL からの再執筆）の時点では push しない（合格後に通常フローで公開する）。
- **承認ゲートなし** — 本ワークフローは人間の承認ゲートを持たない。公開可否は検証ループの合否のみで決まる（`AskUserQuestion` を発火しない）。

## 失敗時の中断ポリシー

- **HTML 執筆失敗時** — HTML 未生成の旨と理由を残し、後続（レビュー・公開）へ進まず打ち切る。push は行わない。`output/*.md` は HTML 工程の前段で出力済みのため、dedup 照合キー（記事の重複判定キー）は保全される旨を中断レポートに明示する。
- **push 失敗時（認証エラー / 非 fast-forward / コンフリクト）** — 自動 retry・force push をせず、中断レポートを返して打ち切る。HTML は生成済みだが未公開である旨、`output/*.md` の dedup 照合キーは保全される旨を明示する。非 fast-forward・コンフリクトを force で踏み潰さない（公開済み履歴の保全）。

中断は「壊さずに止める」ことを優先する。中途半端な公開・履歴破壊を避け、再実行で回復できる状態を保つ。

## 観点別判定基準

`html-reviewer` が担当 1 観点を点検する際の合否基準。観点識別子（`design-consistency` / `readability` / `infographic-richness`）・宣言順・反復制御（反復上限 2 周）は `write-article` SKILL.md が保持し、本節は各観点の「何を見て何を以て PASS/FAIL とするか」を定める。重大度区分・PASS/FAIL ルールそのものは `/multi-aspect-review` に従う。生成側 `article-html-author` も同じ本節を参照して合格基準を満たしにいく（生成⇄レビューの基準共有）。

観点間で責務を分離し重複を避ける: `infographic-richness` は「視覚化の意味的妥当性・過不足」、`design-consistency` は「規約・クラス契約への準拠」、`readability` は「崩れ・可読性」を担当する。

いずれの観点も前述「本文ファクト不点検の原則」に従い、HTML としての整形・デザイン・構造のみを対象とする。

### design-consistency（共有 CSS・レイアウト・コンポーネント規約への準拠）

本スキルが定めるデザイン規約に HTML が準拠しているかを点検する。

- **共有外部 CSS を参照しているか** — 記事 HTML・`index.html` が共有 CSS を `<link>` で参照し、デザインを `<style>` でインライン直書きしていない。配色・余白・タイポを記事 HTML 側で上書き再定義していない。FAIL 例: 記事 HTML 内に独自 `<style>` でレイアウト/配色を定義している、CSS への `<link>` が欠落している。
- **クラス契約に沿っているか** — 「共有外部 CSS」「ページ骨格とレイアウト規約」「記事一覧トップページ index.html の規約」「ビジュアルコンポーネント規約」が定めるクラス（`.article` / `.article__cover` / `.article__title` / `.article__body` / `.glossary` / `.paper-link` / `.article-list` / `.article-card`、およびビジュアルコンポーネントの `.card` / `.card-grid` / `.stat` / `.stat__value` / `.stat__label` / `.compare-table` / `.timeline` / `.timeline__step` / `.diagram` / `.callout` / `.badge` 等）と構造で各コンポーネントがマークアップされている。ビジュアルコンポーネントは規約どおりのクラス・入れ子構造（例: `.card` は `.card-grid` 内、`.timeline__step` は `.timeline` 内、`.stat__value`/`.stat__label` は `.stat` 内）で使われている。FAIL 例: 用語集が `.glossary`＋`<dl>` でなく素の段落で書かれている、カバー画像が `.article__cover` 構造に乗っていない、規約外の独自クラス名でビジュアルを組んでいる、ビジュアルコンポーネントのクラス契約・入れ子構造から逸脱している。
- **骨格の必須要素が揃っているか** — サイトヘッダ／フッタ、カバー画像、タイトル＋メタ、本文、用語集、原論文リンク、一覧への導線が「ページ骨格とレイアウト規約」どおり存在する。`index.html` は並び順規約（新しい順）・重複エントリ無しを満たす。
- **公開元ディレクトリ規約に沿った参照になっているか** — CSS・カバー画像への参照パスが公開元の配置（`docs/articles/`・`docs/assets/`）と整合し、公開後にリンク切れしない相対パスである。

該当観点で**規約からの逸脱は原則 FAIL**とし、逸脱箇所を指摘する。2 周目以降は `previous-review-path` の前回 FAIL 指摘が解消されたかを併せて確認する。

### readability（リッチ HTML の構造妥当性・崩れの有無・可読性）

リッチ HTML として構造が妥当で、表示が崩れず読みやすいかを点検する。

- **見出し階層の妥当性** — `h1`（記事タイトル）→ `h2`（章）→ `h3`（節）が論理順序で入れ子になり、飛び級・順序逆転がない。本文骨格の H2 章立てが成立している。
- **要素マークアップの妥当性** — 段落・リスト・図表（`<figure>`/`<figcaption>`/`<table>`）・引用（`<blockquote>`）・コード（`<pre>`/`<code>`）・数式が、意味に合った要素でマークアップされている。プレーンテキストの羅列で構造を表現していない。
- **崩れ・はみ出しの有無** — 長い表・コード・数式・URL・カバー画像、およびビジュアルコンポーネント（カードグリッド・数値ハイライト・比較表・タイムライン・ダイアグラム）が、狭い画面でもはみ出し・横スクロール破綻・重なり・見切れを起こさない（共有 CSS のレスポンシブ規則・`overflow` 制御に乗っている。狭幅でカードグリッドが段組み解除される、比較表が横スクロール可能になる等）。`viewport` メタが設定されている。
- **可読性の確保** — 本文幅・行間・余白・コントラストが「デザイン観点・品質基準」を満たし、画像に意味のある `alt`、リンクに判別可能なテキストがある。日本語長文として読みやすい。
- **HTML の妥当性** — タグの閉じ忘れ・不正な入れ子がなく、ブラウザで意図どおりレンダリングされる構造である。

表示の崩れ・構造の破綻は原則 FAIL とし、該当箇所を指摘する。2 周目以降は `previous-review-path` の前回 FAIL 指摘が解消されたかを併せて確認する。

### infographic-richness（視覚化の意味的妥当性・過不足）

本文の主要素が「ビジュアルコンポーネント規約」に従って適切に視覚化され、インフォグラフィック風リッチ HTML として本文理解を助けているかを点検する。本観点は「視覚化の意味的妥当性・過不足」を担当し、規約・クラス契約への準拠は `design-consistency`、崩れ・可読性は `readability` が担当する（責務を分離し重複を避ける）。

- **視覚化候補が適切なコンポーネントへマッピングされているか** — 本文中の視覚化候補（主要結果数値・指標／手法間・条件間の対比／手順・時系列・処理段階／処理・関係・因果のフロー）が、意味に応じたビジュアルコンポーネント（数値→数値ハイライト、対比→比較表／カード、手順・時系列→タイムライン／ステップ、処理・関係・因果→ダイアグラム）へ視覚化されている。本文が見出し＋段落＋箇条書きだけのプレーン構造に留まり、明確な視覚化候補が放置されていれば指摘する。
- **装飾過多・情報ブロック過多になっていないか** — 装飾目的だけの図がない。情報ブロックを欲張らない（1 画面・1 セクションあたり 3〜5 個目安）。視線誘導が成立し、視覚化が読み手の理解を助けている（`infographic-design` の設計思想に整合）。過剰な視覚化・読み手を圧迫する密度は指摘する。
- **視覚化が本文の意味を歪めていないか** — 前述「本文ファクト不点検の原則」に従い、視覚化による意味の改変（本文にない数値・対比・因果の捏造、本文と矛盾するハイライト等）がないかを点検する。本文ファクトの正否は再点検しないが、意味の改変は FAIL とする。
- **コンポーネントが崩れていないか（最小確認）** — 視覚化が破綻して意味が伝わらない状態でないか。表示崩れ・レスポンシブ破綻の詳細点検は `readability`、クラス契約準拠は `design-consistency` に委ね、本観点では「視覚化として意味が成立しているか」に絞る。

視覚化候補の取りこぼし・装飾過多・意味の歪みは原則 FAIL とし、該当箇所を指摘する。重大度区分・PASS/FAIL ルールは `/multi-aspect-review` に従う。2 周目以降は `previous-review-path` の前回 FAIL 指摘が解消されたかを併せて確認する。

## DRY 制約

記事仕様は本スキルで再定義しない。次は `japanese-tech-writing` が唯一の真実源であり、本スキルからは参照のみとする（二重定義禁止）。

- **frontmatter の項目・形式** — `japanese-tech-writing` に従う。
- **記事スラッグ・ファイルの命名規約** — `japanese-tech-writing` に従う。
- **用語集の方針・対象用語の選定** — `japanese-tech-writing` に従う（本スキルは用語集の **HTML 構造**＝`.glossary`＋`<dl>` のみを定める）。
- **日本語表記・トーン** — `japanese-tech-writing` に従う。記事タイトル・本文・要約・メタの文言は確定済み `output/<記事>.md` を根拠とし、本スキルで言い換え・捏造しない。

本スキルが扱うのは「HTML としてのデザイン・構造・コンポーネント・共有 CSS・公開規約・観点別判定基準」であり、「記事として何を書くか・どう表記するか」は `japanese-tech-writing` に委ねる。役割を分離することで二重定義による齟齬を防ぐ（DRY）。
